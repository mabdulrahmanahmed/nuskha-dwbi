Nuskha Pharmacies: viva crash course

Every number on the submission form, what it means and how to defend it, in plain English.

All data is synthetic (seed 472). Numbers come from report/report.md and the evidence/ files.

0The 60-second story

If you remember only one paragraph, remember this one.

Nuskha is a made-up chain of 10 pharmacies in Karachi (3 regions: North, East, South). Its data sits in 4 systems on 3 database engines (MySQL, PostgreSQL, SQLite), and those systems disagree on how a branch, product or customer is named. Some purchases are priced in US dollars.

We built a pipeline that extracts the data, cleans it, matches every code to one true product, branch and customer, and loads it into a PostgreSQL warehouse with two star schemas (Sales and Purchases). The warehouse covers 36 months (Nov 2023 to Oct 2026).

We proved the pipeline is trustworthy: every row is counted, rerunning changes nothing, a second batch loads only what changed, and a deliberate crash leaves no damage. On top of the warehouse sit a Power BI report and two AI models (a sales forecast and an anomaly detector). Their results feed a real decision: the purchase budget for Nov 2026 to Jan 2027.

1Words you must know

Examiners love asking "what does X mean?" Each answer below is one or two sentences.

ETLExtract (copy data out of the sources), Transform (clean and standardise it), Load (put it into the warehouse).
GrainWhat exactly one row in a fact table stands for. Ours: one product line on one receipt.
Fact tableHolds the numbers you add up (quantity, amount, margin), plus keys pointing to dimensions.
DimensionHolds the descriptions you filter and group by (date, product, branch, customer, supplier).
Conformed dimensionOne dimension shared by several fact tables, with the same keys and meaning, so you can compare sales with purchases.
Natural keyThe ID the source system uses, e.g. (receipt_no, line_no).
Surrogate keyA number the warehouse invents for each dimension row. It never changes, even if the source code does.
UpsertInsert if the row is new, update if it exists and changed, do nothing if it is the same.
IdempotentRunning the same load twice gives the same result as running it once. Our rerun wrote 0 rows.
WatermarkA bookmark: "I have read everything up to this timestamp." The next batch reads only rows changed after it.
CrosswalkA mapping table that turns every source code (till code, vendor code, branch spelling) into one canonical member.
SCD Type 1Slowly Changing Dimension, Type 1: overwrite the old value and keep no history. Used to fix mistakes.
LineageA record of where each warehouse row came from: which system, which source key and which batch.
ReconciliationProving that counts and money totals match between source and warehouse.
MAEMean Absolute Error: on average, how many rupees the forecast is off by.
RMSERoot Mean Squared Error: like MAE, but punishes big misses more.
PrecisionOf the alarms raised, the share that were real. High precision means few false alarms.
RecallOf the real problems, the share we caught. High recall means few misses.

3The pipeline, layer by layer

Data flows one way, left to right. One notebook (pipeline.ipynb) runs it all in order.

Why keep raw snapshots?
If anyone doubts a number, we can replay from the exact text that was extracted. They are never edited.
Why crosswalks?
Sales spells a branch 2 or 3 ways, Purchasing uses vendor codes and Sales uses till codes. Crosswalks map them all to one member and record how each match was made (exact, rule, alias or description).

It works because every load is an upsert on the natural key: INSERT … ON CONFLICT DO UPDATE … WHERE … IS DISTINCT FROM. If a row already exists and nothing differs, the database skips it, so a rerun writes 0 rows.
fact_purchase PKR (15,342,311.75) is not the same number as the grn_line source amount (12,822,550.51). The source amount mixes currencies; the warehouse converts USD lines to PKR at the Finance rate.

8Star schemas, grain and conformed dimensions

Two business processes (selling and buying), two stars, sharing three dimensions.

fact_sales
Grain: one product line on one till receipt.
Natural key: (source_system, receipt_no, line_no)
Measures: quantity_units, gross_amount_pkr, discount_pkr, net_amount_pkr, cost_amount_pkr, gross_margin_pkr (all additive).
fact_purchase
Grain: one product line on one goods receipt note (GRN).
Natural key: (source_system, grn_no, line_no)
Measures: quantity_units, amount_original (additive within one currency only), purchase_amount_pkr.
Unknown and Walk-in members
Every dimension has an Unknown member (key −1), and dim_customer also has Walk-in (key 0), so fact foreign keys are never null.
Ratios are never stored
ASP, unit cost and margin % are non-additive. You can't add percentages, so the views always recompute them from sums.
Never join the two fact tables directly. That multiplies rows (fan-out). Sales and purchases are each summed to product × month first, then compared. Join safety check: the fact_sales total is the same before and after joining every dimension.

9SCD Type 1: fixing a wrong category

A product was filed under the wrong category. Type 1 overwrites it and keeps no history, because it was a mistake, not a real change.

Effect on category net sales (PKR)

In batch 2 we overwrote P-0368's category in dim_product from Gastro to Cough and Cold, with no history row. Exactly two category totals moved, by ±112,316.85, and the company total stayed at 16,382,871.40.
Type 1 vs Type 2. Type 2 adds a new row with dates to keep history (e.g. a product genuinely moving to a new category). Ours was a correction, so history would be misleading. Type 1 is the right choice.

12The forecast (BQ5)

Predict company-wide monthly net sales for the next 3 months.

Model: Ridge regression
Features (built in SQL, vw_forecast_features): lag_1, lag_12, prior-only 3-month rolling mean, month of year, Ramadan days.

13Anomaly detection (BQ6)

Find region × category months that moved abnormally (24 series, review period Nov 2025 to Oct 2026).

Threshold method: robust z-score
Ratio of each month to its trailing 6-month median; flag if the robust z-score is above 3.5. Simple and transparent.
Model: Isolation Forest
Uses that ratio, the year-on-year ratio and the ratio to the category average. It isolates points that are easy to separate from the rest.

To score them fairly we injected 25 known spikes and drops into a copy of the review period, so we know the right answers.

14The management decision

The examiners want to see a real decision, not just charts.

Decision: setting the Nov 2026 to Jan 2027 purchase budget and stock mix. The warehouse gives one reconciled monthly sales history across all branches. The dashboard shows the trend and the December to February Cough and Cold peak. The forecast gives a range for each month (about PKR 617k, 611k and 630k). Diabetes Care supplier. Margin fell from 25.56% to 16.46%. The margin bridge blames cost (a 12% rise from March 2026 with shelf prices frozen), not price or volume, so renegotiate or switch the supplier.

16Rapid-fire viva Q&A

Try to answer each one out loud before opening it.

Why two fact tables instead of one?

Selling and buying are different business processes with different grains (receipt line vs GRN line) and different dimensions (customer vs supplier). One table would mix grains. They share Date, Product and Branch, so they can still be compared after summing each to product × month.

What is the grain of fact_sales, and why that grain?

One product line on one till receipt. It is the lowest level the source has, so any total (by day, branch, category, customer) can be built by adding up. You can always roll up, but you can never drill below your grain.

How do you know no row was lost?

Row reconciliation per table per batch: 32,944 = 32,147 + 635 + 162. Amounts too, month by month, to the paisa, with 0 difference. Every reject matches the defect ledger key for key.

What is the difference between a duplicate and a legitimate repeat?

A duplicate is the same line exported twice (all columns identical, the D01 defect): 162 removed. A legitimate repeat is a real second purchase that looks similar: 278 kept. Deleting repeats would understate sales.

Why does the rerun write 0 rows?

Loads are upserts on natural keys with IS DISTINCT FROM, so unchanged rows are skipped. Row counts, totals and MD5 fingerprints were identical before and after.

What is your watermark and where is it stored?

updated_at on transaction tables, stored in etl.batch (watermark_from and watermark_to). Batch 2 read rows updated after 2026-08-31 23:59:59. Master tables are small, so they are extracted in full each batch.

A late receipt arrives in batch 2. Which month does it go into?

Its real transaction month (July or August 2026), not the load month. The date key comes from the receipt date. 40 such receipts, trace T3.

How do you handle deletes in the source?

A key comparison between batches found the 3 deleted receipts. They are logged in etl.deletion_log and kept in the fact table for audit, not deleted.

What if a new product appears in the facts before the dimension?

Late-arriving dimension: the dimension upsert runs before the fact load in each batch, so P-0500 got its surrogate key first. Anything still unresolved maps to the Unknown member (−1), so foreign keys are never null.

What happens if the load crashes halfway?

The fact load is one transaction. With FAIL_AT=0.5 it failed after 1,184 of 2,369 rows, rolled back, and the batch was marked FAILED. Totals and fingerprints were unchanged. The rerun matched the clean run.

Why SCD Type 1 and not Type 2 for P-0368?

It was a data-entry mistake (Gastro instead of Cough and Cold), not a real change over time. History of a mistake is misleading. Exactly two category totals moved by ±112,316.85 and the company total did not change.

How are USD purchases converted?

At the Finance fx_rate on or before the receipt date. Lines with no rate available are rejected with code R06 (4 in batch 1). Trace T2 shows one.

Why can't you add up margin %?

Percentages are non-additive: the average of two branch margins is not the company margin. We store margin in PKR (additive) and recompute % = sum(margin) / sum(net sales) in the views.

How do you prove Power BI is correct?

Three totals under the same filters match warehouse SQL exactly: FY2026 net sales 6,230,294.70, Gulshan-e-Iqbal 2025 745,398.10, October 2026 purchases 599,167.14.

Your forecast lost to a naive baseline. Isn't that a failure?

It is an honest result. Only 21 usable training rows after lag-12, and sales are smooth month to month, so "same as last month" is hard to beat. We report it, avoid leakage (tested), and use the forecast range for the decision with a monthly revision.

How did you avoid data leakage in the forecast?

Features use only prior months (lag_1, lag_12, a prior-only rolling mean), alpha was tuned inside the training months by rolling-origin validation, and the holdout (Aug to Oct 2026) was never touched during training. A leakage test file proves it.

Explain precision and recall with your numbers.

Isolation Forest raised 22 flags; 20 were real, so precision = 20/22 = 0.91. Of the 25 injected cases it caught 20, so recall = 20/25 = 0.80. The z-score caught only 6 (recall 0.24) with 4 false alerts (precision 0.60).

Why inject anomalies instead of using real ones?

To measure precision and recall you need to know the right answers. Injected cases give a labelled test set. We also traced 3 real flags to their receipt lines.

Where are the AI results stored, and what if the AI job runs twice?

In the separate ai schema (model_run, forecast_result, anomaly_result), never in the dw facts. The run id is a hash of the configuration and the data batch, so a retry upserts the same rows: 0 duplicates.

How would you add a new department, e.g. Home Delivery?

The bus matrix shows it: a new fact table reusing the conformed Date, Branch and Customer dimensions, with no redesign of the existing stars.

What is the biggest limitation?

The data is synthetic, so the methods are shown to find what was planted, not tested on real-world mess. The forecast has very few training rows, and the anomaly evaluation uses only 25 injected cases.
