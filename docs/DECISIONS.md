# Decisions and deviations from the blueprint

| Unit | Decision | Reason |
| --- | --- | --- |
| plan | The warehouse PostgreSQL runs in the build environment (and in Colab), not on a hosted service. | A hosted service needs a person to create an account and share credentials; the plan must run without human input. |
| plan | Power BI reads CSV exports of the saved views (`powerbi/data/`) instead of a live database connection. | Power BI Desktop cannot reach a database inside a container; the three reconciled totals are checked against SQL totals from the same batch. |
| plan | Evidence is committed to the git repo after every unit instead of a Google Drive folder. | Removes the Drive mount, which needs a person to sign in. |
| plan | The notebook is executed headlessly on Ubuntu first; the Google Colab run is the last human step. | Colab cannot be driven without a person; Ubuntu matches Colab's environment. |
| plan | All human steps are moved after the automated build, except the setup that starts it; a closing automated step runs after them. | Requested by the user: no human input during the run. |
| plan | A unit that fails 3 times is BLOCKED and its dependents SKIPPED instead of stopping the run. | The run never waits for a person; blocked units are fixed at the end. |
| plan | The build runs locally in a terminal (Ubuntu on WSL, or macOS) instead of a Codespace. | Requested by the user. Progress is committed after every unit so a laptop shutdown loses nothing; `scripts/resume.sh` continues. |
| plan | Evidence is committed to the local git repository after every unit; pushing to GitHub is optional backup. | No account is needed for the run itself. |
| setup | `scripts/run_all.sh`, `run_phase.sh` and `finalize.sh` pick the interpreter as `.venv/Scripts/python`, then `.venv/bin/python`, then `python3`/`python`, instead of a hard-coded `python3`. | The build machine is native Windows (Git Bash), where `python3` does not exist; the same scripts still work on WSL, macOS and Colab. |
| setup | The git repository was initialised in the project folder with a "Project kit" commit before unit 1.02. | CLAUDE.md requires a commit after every unit; the kit had no repository yet. |
| setup | The venv is created with `--system-site-packages` and reuses the machine's global numpy, pandas, matplotlib, scikit-learn and psycopg2-binary; only the missing small packages are pip-installed into it. | The network on the build machine downloads at about 10 KB/s, so a full `pip install -r requirements.txt` would take hours. `requirements.txt` is unchanged, and Colab installs it normally. |
| 1.04 | Generator randomness uses `numpy.random.default_rng([472, part])`, with one part number per generator part (1 reference, 2 transactions, 3 defects, 4 stage-2 changes). | Still seed 472, but changing a later part never shifts the random numbers of an earlier part, so earlier evidence stays valid. |
| 1.04 | Prices and costs rise 8% every 1 July (2024, 2025, 2026). Diabetes Care cost rises a further 12% on 1 Mar 2026, and its shelf price is frozen (no July 2026 rise). | Implements the blueprint's "price inflation" and the Diabetes Care margin story; ASP stays flat while cost rises. |
| 1.04 | Ramadan dates (approximate, synthetic) are 2024-03-12..04-10, 2025-03-02..03-30 and 2026-02-19..03-20 (`data/generated/reference/ramadan.csv`, also in `src/gen/catalogue.py`). | Needed for the Vitamins season and for `dim_date.is_ramadan` (unit 3.02). |
| 1.05 | Product popularity falls with shelf price (popularity ∝ lognormal / price^0.7, then scaled to each category's line share). | Cheap items selling more is realistic, and it keeps a few expensive items from dominating each month's value, so the seasons and trend show clearly. |
| 1.05 | The planted stock-out is Gulshan-e-Iqbal (BR-GUL, the largest East branch), June 2026, with 5% of normal receipts kept. | Anomaly detection works at region × category grain, so the branch drop has to be large enough to move its region's series. |
| 1.05 | Late arrivals (40 receipts from Jul–Aug 2026 with `updated_at` in Sep–Oct 2026) are created in the transactions part, so they are absent from stage 1 and first appear in stage 2. | A late receipt does not exist in the Sales database until it syncs; this keeps stage-1 output independent of the stage-2 part. |
| 1.05 | A source row belongs to a stage when its `updated_at` is on or before the stage cut-off (stage 1: 2026-08-31 23:59:59; stage 2: 2026-10-31 23:59:59). Master tables keep what existed by then. | One simple rule makes both snapshots consistent with watermark extraction. |
| 1.06 | D01 exact duplicates are listed by the generator in `data/generated/stage<N>/double_export.csv` (the till/GRN export job sends these keys twice). The extract step (2.02) must append those rows a second time to its raw snapshot of that table, which reproduces the double export. | Every source table has a primary key, so a duplicate key cannot be stored in the source itself; the blueprint defines D01 as "same source key extracted twice". |
| 1.06 | R07 orphan lines are planted only in Sales (the header row is removed, its lines stay). Unit 1.08 must load Sales with `SET FOREIGN_KEY_CHECKS=0`. Purchasing (PostgreSQL) enforces its FKs, so it gets no orphans. | A legacy till sync can lose a header; PostgreSQL would refuse the rows. |
| 1.06 | R01 rows use till codes and vendor codes that exist in `pos_item`/`vendor_item` but match no Inventory item (MISC-OPEN, DISC-0412-STR, SAMPLE-PCS; ZZZ-0001, ZZZ-0002). R03 rows have their date keyed 10 years ahead. R04 rows have price or cost 0 or negative. U01 rows are panel receipts with junk panel text. | These keep the source FKs and NOT NULL constraints valid while still being rejected by the ETL rules. |
| 1.06 | Each line carries at most one defect code, and header-level defects (R03, R05, R07, U01) cover every line of the chosen header. R06 is 4 lines on two USD GRNs received 27 and 30 Oct 2023, before the first FX rate. | Reject counts per code then add up exactly, and the ledger can be compared one-to-one with `etl.rejects` in 2.08. |
| 1.07 | Stage 2 is written as a full snapshot of every source table on 31 Oct 2026 (`data/generated/stage2/`), not as a list of changes. Batch 2 (3.05) reloads the sources from it and extracts by watermark. | It mirrors what a real source looks like after two months of activity, and the diff (`stage2_diff.csv`) proves only the intended rows changed. |
| 1.07 | Any edit (quantity fix, panel-name fix, void, GRN cancellation) re-saves the whole document: the header and all its lines get the new `updated_at`. | Watermark extraction then sees every line of an edited receipt; this is how many POS apps behave. |
| 1.07 | Stage 2 adds one new product (item 500, Paracetamol 1000 mg, PAR-1000-STR, vendor code with the Paracetamol 500 mg supplier's prefix), launched 1 Sep 2026 and sold on 40 Sep–Oct lines. | Exercises the blueprint's "late-arriving dimension" rule (dimension upsert before facts in the same batch). |
| 1.07 | Panel-name corrections cover all 8 stage-1 receipts with junk panel text (the plan's "about 10"). | Only 8 U01 receipts exist in stage 1 (20 lines at the planted 1% rate). |
| 1.09 | ERD PNGs are drawn with matplotlib when the Graphviz `dot` program is missing. The `.dot` files are always written, and `python -m src.erd` renders them with Graphviz automatically once `dot` is on PATH. | Graphviz is not installed on the build machine, and installing system software is outside the project folder; the plan's "render in 1.08" would hit the same gap. |
| pre-DB | Box sizes are 5–10 strips (6–12 bottles or pieces), and GRN lines receive 1 + Poisson(0.6) boxes (was 10–30 strips and 1 + Poisson(2.5)). | The first sizes made purchases about 6.6× the cost of goods sold (81.5M vs 12.3M PKR); purchases are now 16.5M PKR, a plausible amount of buying for this level of sales. All generator checks were rerun and pass; some later random draws shifted (Poisson draws use a variable amount of randomness), so the 1.05–1.07 evidence files were regenerated. |
| pre-DB | Before the databases existed, the ETL, views and later analytics were developed on an in-memory dry run and a DuckDB copy of the warehouse (`src/offline_dry_run.py`, `src/offline_warehouse.py`, file `data/offline_dw.duckdb`). `duckdb` and `sqlglot` are dev-only tools and are not in `requirements.txt`. | The person's database credentials were not available (docs/BLOCKERS.md). The same SQL files run on PostgreSQL later; DuckDB accepts the PostgreSQL syntax they use. |
| pre-DB | `vw_forecast_features` has one extra column, `ramadan_days`, beyond the blueprint's columns. `vw_margin_bridge` splits the month-on-month margin change into volume, price and cost effects that add up exactly. `vw_region_category_month` uses a correlated subquery for the trailing 6-month median. | The model needs a Ramadan flag; an exact additive bridge is easy to defend; PostgreSQL cannot use percentile_cont as a window function. |
| pre-DB | GRN units, currency and FX conversion are applied after joining each line to its GRN header and purchase order (`normalize.convert_purchase_lines`, called in `quality.py`), and header tables are cumulative across batches. | A September GRN can belong to an August purchase order extracted in batch 1. |
| pre-DB | The keying-error pattern is planted on the most expensive South Cardiovascular walk-in strip line of Apr 2026 as "qty 80 instead of 8" (was "60 instead of 6" on an arbitrary cheap line). | The first version added only about 30% to its region-category month, so no fair detector would flag it, and the planned case review could not work. |
| pre-DB | Anomaly detection adds a transparent region-wide pattern rule: 5 or more of a region's 8 categories below robust z −1.5 in the same month. In the review period it flags exactly East, June 2026. | A one-branch stock-out lowers every category of its region by about half, but no single cell crosses z 3.5. The pattern rule finds it, and the case review traces it to branch level (Gulshan-e-Iqbal: 5 receipts against a usual ~50). |
| pre-DB | The injected-anomaly evaluation copy is stored under its own run_id (`<run_id>-injected`), with its own `ai.model_run` row. | The blueprint's unique key for `ai.anomaly_result` (run_id, date_key, region, category, method) would otherwise collide between real and injected rows. |
| pre-DB | The robust z-score uses the median and MAD of ratio_to_trailing pooled over all 24 series in the calibration months. Isolation Forest uses 300 trees, contamination 2% and random_state 472. | About 18 calibration points per series give an unstable MAD; the ratio has no units, so pooling across series is fair. |
| pre-DB | The forecast uses a recursive 3-month-ahead setup: each predicted month feeds the next month's lag_1, for both the holdout and the rolling-origin validation. Alpha is chosen from {0.1, 1, 10, 100, 1000}, and the forecast range is ±1.28 × the rolling-origin RMSE. | It is honest: the holdout is forecast from its origin, like the real Nov–Jan forecast. |
| 1.01 | MySQL root / PostgreSQL postgres passwords were unknown, so `scripts/reset_db_access.ps1` (run once by the person as Administrator) uses each engine's documented recovery method to create the `nuskha` user. | The person did not know the admin passwords set at install time. |
| 2.02 | The first batch-1 extract was discarded and rerun after fixing the amount comparison (NaN vs None); the rerun's snapshot was byte-identical. | The data was right; only the check was wrong. |
| 2.04 | Staging is rebuilt from the immutable raw snapshots for each step; stg.* tables in the warehouse are written as the result (NUMERIC money, typed dates), header tables cumulative over batches. | The pure-pandas pipeline was proven in the dry run; recomputing from raw keeps every step deterministic and rerunnable. |
| 3.05 | "Updated in place" counts only lines whose warehouse values change (71); 21 lines re-saved with only a new updated_at are correctly left untouched by the upsert. GRN cancellations are 7 lines (the stage-2 change list), not 9. | The upsert rewrites a row only when a value differs, which is the rerun-safety rule. |
| 3.07 | The controlled failure and its rerun run under their own etl.batch rows (3 FAILED, 4 SUCCESS) loading the batch-2 snapshot. | Keeps batches 1 and 2 as the two real loads while showing FAILED -> rollback -> clean rerun. |
| 3.10 | Traces 5 and 6 use the views, so the views (unit 4.01 SQL) were created during 3.10; 4.01 reruns them and its checks. | Trace order in the blueprint needs the view layer. |
| 3.11 | Validation check 11 (AI outputs after a retried run) is NOT RUN until phase 4 fills the ai tables; the full suite is rerun in 5.09. | The check has nothing to inspect before the AI units. |
| 4.02 | PostgreSQL DATE/NUMERIC results are converted to pandas datetime/float (`src/queries.py: pg_types`) before the readings and the AI code use them. | DuckDB returned those types natively; the same code now runs on both. |
| 4.05 | The ridge forecast (holdout MAE 70,806) loses to last-month naive (56,347) and beats seasonal naive (116,207); reported as is. | Blueprint: "The model does not need to win; the comparison must be honest." Only 21 usable training rows. |
| 4.10 | Report pages written in PBIR (report 3.0.0, page 2.0.0, visualContainer 2.4.0) by `src/powerbi_report.py`; validated with jsonschema against the schemas Microsoft publishes on GitHub. Visual 8 sorts by Net Sales (Top N added by hand per BUILD_GUIDE). | No Power BI Desktop in the build; schema validation is the strongest automatic check available. |
| 5.02 | The headless run is `python -m src.headless_run` (nbconvert executes `pipeline.ipynb` twice with NUSKHA_MODE=FULL_REBUILD and compares the 11 warehouse totals). Only one executed copy is kept (`evidence/05_validation/headless_run/pipeline_executed.ipynb`). A few list-type evidence CSVs (stage2_intended_changes, stg_column_types, meta_column_map, stage logs) change row order or timings between runs; their contents are identical. | The two executed notebooks differ only in timings; the totals comparison is the acceptance evidence. |
| 5.07 | `src/pipeline.py` gained `--from/--to` step ranges so the live demo rebuilds the warehouse from empty in seven commands, each a range of the notebook's steps. | The demo then shows real runs without leaving the warehouse half-rebuilt, and every demo command is the code the notebook runs. |
| 5.08 | Viva guides written per rubric owner (`docs/viva/member1..4.md`), each with component, connections, numbers (with source file), 15 Q&A and live "show me" commands. | Blueprint ownership table: one criterion per member. |
| 5.09 | `evidence/03_warehouse/load_log_batch_1.csv` is rewritten by the rerun test (same batch id), so it shows the rerun's 0 inserted / 0 updated. The first batch-1 load is evidenced by `fact_checks_batch_1.csv` (27,543 / 4,604 rows, amounts to the paisa) and `meta.lineage`. Left as is; noted in the audit. | Changing the log naming would need another full rebuild for no change in the data. |
| post-1.0 | `src/powerbi_model.py` writes the Power BI `DataFolder` parameter as the absolute path of this checkout's `powerbi/data` (was the placeholder `C:\nuskha-dwbi\powerbi\data`, which made every table fail to load). | The .pbip opens with data on the machine that generated it; on another PC, rerun `python -m src.powerbi_model` or edit the parameter (Transform data → Edit parameters). |
| post-1.0 | The Top N = 10 filter on the top-products table (Diagnostic page) is written by `src/powerbi_report.py` (`topn_filter`, the JSON Power BI Desktop writes) instead of being added by hand. | Regenerating the report (demo step 6) no longer drops the filter. |
| post-1.0 | `scripts/check_env.py --create` connects to MySQL through `information_schema` to run CREATE DATABASE. | `url.set(database=None)` keeps the old name in SQLAlchemy, so on a fresh server (Colab) the missing databases were never created (error 1049). Found in the first Colab run. |
